DOGFOOD (owner, 2026-09-15, on v0.11). In `aira board`, pressing Home/End jumps the cursor to the first/last card in the focused column, but the NEXT arrow key (↑/↓ or j/k) jumps BACK to the selection from BEFORE Home/End — not one step from the Home/End position. Home/End are effectively cosmetic and the selection desyncs.

ROOT CAUSE: captureBoardInput (cmd/aira/tui_board.go) maps ←/→/↑/↓ and h/j/k/l to board reducer actions (boardMoveColumn / boardMoveCard) that update the AUTHORITATIVE bs.Selected[col]. It does NOT intercept KeyHome / KeyEnd / KeyPgUp / KeyPgDn, so those fall through to the focused tview Table's built-in row navigation, which moves the Table's own selected row WITHOUT touching bs.Selected. renderBoard re-applies bs.Selected via table.Select(...) on every render, and the next arrow runs boardMoveCard from the STALE bs.Selected — so the cursor "returns to the previous selection ±1". The AIRA-254 info pane also keys its detail off bs.Selected, so the pane never follows a Home/End jump either. Same class affects PgUp/PgDn.

FIX DIRECTION: intercept Home/End (→ first/last card in the focused column) and PgUp/PgDn (→ page within the column) in captureBoardInput, mapped to NEW reducer actions (e.g. boardActCardFirst / boardActCardLast, boardActCardPageUp / boardActCardPageDown) that set bs.Selected[focus] and re-arm the info-pane detail exactly like the existing boardMoveCard path. Then the reducer stays the single source of truth for selection and the tview Table's built-in nav is never the authority. Tests: pure reducer tests for the new actions (clamped at column ends, empty column) + a SimulationScreen test asserting Home-then-↓ moves from the Home position, not the pre-Home one (the current tests don't exercise Home/End, which is why this shipped).

SEVERITY P2: always-reproducing navigation bug in the shipped read-only board; recoverable (arrows still work), no data loss. Follows AIRA-254.
