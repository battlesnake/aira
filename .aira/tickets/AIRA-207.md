confine's CLI-layer argument refusal writes only to stdout when stdout is not a TTY, so a script capturing stderr sees an empty diagnostic for a launch that never ran
**kind** bug · **severity** P2 · **closes** RANT-33

**SYMPTOM.** A peer project hardcoded `aira confine --admit-timeout 300 -- <cmd>`; `--admit-timeout` parses with `time.ParseDuration`, so a bare `300` is refused and **every confined launch in that project silently lost confinement**. The refusal is honest but lands on the stream a script does not read: with stdout piped, exit 2, the JSON envelope on stdout, stderr 0 bytes. Every other confine diagnostic goes to stderr — the run trailer (`internal/runner/confine_linux.go:1457`), the shim trailer (`confine_shim_linux.go:488`) and AIRA-147's never-ran envelope (`confine.go:885-892`). Two aggravations: **the same flag splits its own refusals across two streams** (`--admit-timeout 48h`, over the 24h `AdmitWaitCeiling`, is caught by the *second* validator and goes to stderr as plain text), and **exit 2 cannot carry the fact** — confine's exit code is a documented pass-through of the job's own (`confine.go:799-816`), so exit 2 is byte-identical to a job that ran and exited 2. That ambiguity is exactly why AIRA-147 built the `ran=no` envelope — and a CLI-layer refusal never enters `runner.Confine`, so it emits no such line.

**ROOT CAUSE.** `cmd/aira/main.go:109` sets `renderJSON := jsonOutput || !stdoutIsTerminal(stdout)`; the shared parse-error path at `main.go:172-177` renders with `renderJSON`, and `render` writes the JSON envelope to stdout when true and `response.Error` to stderr only when false — so a human at a terminal gets stderr and a script gets stdout, the wrong way round. The file states the opposite intent three lines above the bug: `main.go:105-108` says verbs that do not route through the generic decision "deliberately keep using the explicit jsonOutput flag ... confine and friends". Confine's runtime paths honour that (`main.go:213-219`); its parse-error path does not. That one argument is the whole defect. Second validator: `parseConfineArgs` (`main.go:931-941`) checks only the ≥1 ms floor while `runConfineCommand` re-checks and additionally enforces `runner.AdmitWaitCeiling`, writing plain text to stderr.

**PROPOSED FIX.** (1) Special-case the confine family in `main.go:172-177` the way `worker-admit` already is immediately above: keep the stdout JSON envelope exactly as it is and **additionally** write the refusal to stderr — preferably via `runner.FormatConfineNeverRan`, so a CLI-layer refusal produces the same `ran=no` line an in-funnel refusal already does and callers have one fixed string to key on. (2) Hoist the `AdmitWaitCeiling` check into `parseConfineArgs` so one flag stops emitting on two streams. (3) Document the grammar in generated help: `internal/core/core.go:1799-1801` spells out the memory grammar with examples while `core.go:1809`'s `--admit_timeout` entry gives none — give `--admit_timeout`/`--timeout`/`--cpu_timeout` the same treatment, explicitly noting that a bare number means **bytes** on the adjacent `--memory-reserve`. (4) Small fold-in: `internal/pylib/aitest/__init__.py:236-243` warns on both clamp branches and stays silent on the discard branch, so `AIRA_AITEST_ESTIMATED_BYTES=4G` is ignored with no signal while `aira worker-admit --estimated-bytes` accepts `4G` for the same quantity. One `sys.stderr.write` closes it. (Not a correctness gap — `internal/core/skill.go:335` and `README.md:108` document it loudly.)

**HOW TO TEST.** In `cmd/aira/confine_test.go` beside the existing `--admit-timeout` cases: for `--admit-timeout 300`, `500us`, `48h` and `--memory-reserve 4Q`, assert the exit code **and** that stderr contains `E_CONFINE_ARGUMENT_INVALID`. Rows 1, 2 and 4 fail today with empty stderr; row 3 passes, which is the inconsistency fix (2) removes. `runWithInput` takes `io.Writer`s and a `bytes.Buffer` is not an `*os.File`, so this is exactly the scripted case. If (1) uses `FormatConfineNeverRan`, tighten to `runner.ConfineNeverRanFacet`.
