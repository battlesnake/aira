Field data (various' BL-875 merge-gate engine leg, 2026-08-30): a fresh -n auto suite BLANKED with the AIRA-11 signature (exit 5, 'no tests ran in 1.58s', collection abort) DESPITE both AIRA-11 (ionice best-effort-7, banner-confirmed) AND AIRA-14/Slice-1 (cpu-weight aging, banner-confirmed cpu-weight=aging). The blank is pure PRE-PLUGIN execnet bootstrap (interpreter spin-up + imports), which runs BEFORE pytest loads the aira_xdist_governor plugin. Consequence: NEITHER Slice-1 (cpu.weight aging) NOR Slice-2 (the daemon active-set EXECUTION scheduler) can DIRECTLY gate it — Slice 2 helps only INDIRECTLY by bounding steady-state execution workers to free CPU for a fresh bootstrap. That covers the 'one fresh suite amid steady-state load' regime but NOT the 'multiple suites simultaneously cold-starting' regime (all bootstrapping at once, before any reaches the execution gate). The real fix for the simultaneous-cold-start regime is a WHOLE-SUITE bootstrap-admission: gate 'aira confine -- pytest' STARTS (not per-test) so only ~ncores/n_workers suites bootstrap concurrently. Open questions: where to gate (confine admission already exists for RAM — extend to a CPU-bootstrap slot?), how to size (a suite's bootstrap needs ~n_workers cores briefly), how to avoid deadlock/starvation (a suite must eventually bootstrap), fail-open when the daemon is down. Depends on Slice 2 landing (the daemon scheduler + governor socket are the substrate). various committed to capturing pgrep -af pytest + aira confine --list at the next blank to classify concurrent suites as bootstrapping vs executing — that regime signal decides whether Slice 2 alone suffices or this ticket is needed. Relates to AIRA-11, AIRA-14, and the cooperative-scheduler design (docs/superpowers/specs/2026-08-30-aira-cooperative-scheduler-design.md §3.2 bootstrap bullet + §5.2).

## Resolution (2026-09-05, backlog-completion triage)

**Superseded by:** AIRA-30 (aitest, `2692053`) + AIRA-64 (`50a5b62`); residual xdist-leg exposure is owned by AIRA-33 (xdist-stack retirement), gated on AIRA-91

The ticket's concern is xdist-specific: `-n auto` spawns N execnet interpreters that each import the full dependency tree BEFORE any pytest hook, so under simultaneous cold-start of several suites the bootstrap storm can blank (exit 5, "no tests ran"). Its proposed fix was a whole-suite CPU-bootstrap slot at `aira confine -- pytest` start, built on "the daemon scheduler + governor socket" (Slice 2, `internal/daemon/governor.go`).

Verified against current source, every load-bearing premise has changed underneath it:

1. The governed pytest stack is now aitest (AIRA-30, done, squash `2692053`, 2026-09-02). Its supervisor imports and collects ONCE in-process (`internal/pylib/aitest/supervisor.py:613-616` — "Session collection already ran in this process before bootstrap"), then workers are COW `os.fork()`s, each individually admitted via the daemon `worker-admit` verb before it runs anything. There is no N-interpreter execnet bootstrap phase to gate, and in-process collection has no gateway timeout, so the "blank" failure mode does not exist in that stack. The AIRA-30 commit message states this explicitly: it "closes ... AIRA-17/26's ungoverned bootstrap window (workers only exist after an admitted fork, so there's no pre-hook import phase)".

2. The cross-suite CPU-oversubscription regime the ticket worried about is now bounded directly, not "only indirectly": AIRA-64 (done, `50a5b62`, 2026-09-05) folds a machine-wide CPU-concurrency bound into `worker-admit` — `s.cpuSlotsDecide(...)` at `internal/daemon/worker_admit.go:644` and `:695`, policy in `internal/daemon/cpuslots_gate.go:190`, capacity from `cpuslots.go:desiredCPUSlots` (NumCPU − reserve) with a per-job liveness floor.

3. The substrate the ticket names as its dependency ("the daemon scheduler + governor socket", `governor.go` park/active-set) is confirmed clientless: AIRA-64's required grep sweep found no non-pytest caller, and it is CUT-eligible under AIRA-33, which deletes `internal/pylib/aira_xdist_governor`, `internal/runner/governor_slot.go`, and `daemon/governor.go`. Building a new admission slot into a stack scheduled for deletion is precisely what CLAUDE.md's simplicity rule and the project's own plans reject.

4. Three planning artifacts already dispose of this ticket the same way: the Fable backlog sweep (`docs/superpowers/reviews/2026-09-04-fable-backlog-simplification-sweep.md:169`, "close as superseded by the already-planned xdist-stack retirement (AIRA-33)"), the backlog-remediation plan (`:956`, "no separate action; auto-resolve when AIRA-33 lands"), and AIRA-33's own body (`:39`, "AIRA-17 ... close automatically with this deletion"). The simplification-programme plan (`:222`, `:994-996`) says "do not leave it open pointing at deleted code" and flags only "owner's call" because the field data came from a project still on xdist — which I checked and can scope (point 5).

5. The one honest residual: xdist `-n auto` IS still live in the field. fastest-ee `origin/master` pins hosted/services/pipeline to `FASTEST_NO_AITEST=1` → plain xdist (`Makefile:330-402`, `scripts/merge_gate.sh:976-984`) because of AIRA-91/92, and test-lite-slowbuild deliberately routes to xdist (AIRA-100). So the exact failure mode can still physically occur on those legs during the AIRA-91-gated window. But (a) no bootstrap blank has been reported in any ticket since AIRA-11 (ionice) and AIRA-14 (cpu.weight aging) shipped — a grep of all tickets for "no tests ran"/"blank" hits only AIRA-11/14/17 and AIRA-91 (a different, exit-137 failure); the ticket's own decisive signal (pgrep + `confine --list` at the next blank) was never captured; (b) the engine leg where the original blank was observed now runs on aitest; (c) that transitional exposure is already owned by AIRA-33's precondition (AIRA-91 Part A + unpin), not by this ticket. AIRA-33 is still `planned` and AIRA-91 Part A is not yet landed (master HEAD `61b83e5`), so "auto-resolve when AIRA-33 lands" would leave this open for an unknown further period pointing at a mechanism nobody intends to build — closing it now as superseded is more honest than that.
