DEFERRED (owner chose to stop at per-worker-admission Slice 1, 2026-09-01). Relates AIRA-17 (whole-suite bootstrap-admission) — the RAM half of the same simultaneous-cold-start problem.

PROBLEM: under wide `-n`, N xdist workers spin up and each imports (~256MiB baseline) simultaneously. Against a nearly-full slice, N×baseline of simultaneous import allocation can overshoot the cap before anything reserves it. Slice 1's per-test reserves are acquired only AFTER a worker starts running, so they don't gate the import.

KEY FINDING (Sol, plan-review 2026-09-01) — why the "per-worker base lease" idea (the original Slice 2) DOES NOT solve this: a base measured/charged POST-import is already resident in memory.current when charged, so a PEAK-class base is subsumed by current instantly — a no-op that never gates cold-start. Genuine protection needs a PRE-IMPORT gate.

DESIGN DIRECTION: reserve a CONSTANT per-worker floor K (B is unknowable pre-import) BEFORE the worker imports — i.e. the worker must be admitted for ~K before it is allowed to import/run — and release/subsume K once its real baseline is resident in current. The hard part is the PROTOCOL: the reservation must happen before the pytest worker's module imports, which is before the plugin's pytest_runtest_protocol hook — likely needs a conftest/worker-start hook or an execnet-bootstrap-level gate (which is exactly AIRA-17's regime, structurally before any plugin hook). Consider whether one pre-import-gate mechanism can serve BOTH the RAM cold-start (this) and the execnet bootstrap blank (AIRA-17).

WHY DEFERRED: genuinely valuable but a hard protocol change (pre-plugin/pre-import); Slice 1 delivered the big win without it; not currently a reported blocker. relates: AIRA-17, the class-split tightening ticket, Slice 1.

What I verified against the current tree (not the ticket's framing):

1. The premise (N simultaneous per-worker imports) no longer exists on the supported path. AIRA-30 (`2692053`, done) replaced the xdist worker model. In /home/mark/claude/aira/internal/pylib/aitest/supervisor.py `run()` (lines 1906-1925) the supervisor calls `bootstrap()` (self-relocates into `.aira-supervisor`), then `gc.freeze()`, and only then `spawn_worker()` per worker. `spawn_worker` (lines 998-1001) calls `self.acquire_worker(estimated_bytes, ...)` — the daemon `worker-admit` connection-held lease — BEFORE `fork_worker(grant["scope"])`. Workers are `os.fork()`ed from the already-imported supervisor and COW-share its import state (spec /home/mark/claude/aira/docs/superpowers/specs/2026-09-01-aitest-design.md §3.1 lines 82-92, §3.3 lines 263-271). There is exactly ONE import per suite (the supervisor's), and each worker's footprint is admitted before the worker process exists. That is structurally the "reserve before the worker is allowed to import/run" gate the ticket asks for — achieved by deleting the per-worker import rather than by gating it.

2. The per-worker admission is not a no-op of the kind Sol flagged (a post-import PEAK base subsumed by `memory.current`). `evaluateWorkerAdmit` (/home/mark/claude/aira/internal/daemon/worker_admit.go:431) checks the OUTER scope's live `memory.current` AND a worst-case aggregate guard: Σ(already-granted worker `memory.max`) + supervisor scope RSS must fit under the ceiling (worker_admit.go:560-585, with the explicit worked example of 600M supervisor + 8×970M workers). Each worker gets a hard `memory.max`. So simultaneous worker growth toward peak is bounded pre-fork.

3. The aitest analog of the ticket's scenario — several suites cold-starting at once — reduces to N supervisors each importing once. Each supervisor is an ordinary `aira confine --delegate-ram` job whose slice-ledger reserve is resolved pre-launch by `ResolveConfineReserve` (/home/mark/claude/aira/internal/runner/confine_linux.go:495; pinned `DefaultDelegateRAMOverhead` = 512MiB at /home/mark/claude/aira/internal/runner/confine.go:25, or a declared `--memory-reserve`, or history). That is a whole-job pre-launch gate — the only residual is reserve ACCURACY (a supervisor whose import exceeds the pinned overhead grows live under `max(effectiveCurrent, outstanding+adopted)`). That residual is already written down as AIRA-29 v2 item (2) "class-correct cold floor — delegate uses the suite-peak ceiling not the 512MiB overhead"; AIRA-29 is on hold pending an owner decision and is the right home for it. It is a single-process growth race in the general admission class, not AIRA-26's N×worker-import burst.

4. The legacy xdist governor is still physically in tree (/home/mark/claude/aira/internal/pylib/aira_xdist_governor/, still armed by `--delegate-ram` per AIRA-77), so the concern is not "already-done" there.
