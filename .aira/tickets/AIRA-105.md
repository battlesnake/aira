Recorded honestly: the specific instance field found had already cleared by the time it was investigated, so this is a credible report with partial independent grounding, not a reproduced-and-confirmed bug.

## What field reported

`aira confine --list` showed `slice reserve: 62725860K granted / 63232M ceiling` with a queued waiter, while the machine had ~45GB genuinely free. One "adopted scope" in the table: `SUPERVISOR-PID 4096382`, `LIVE no`, `LEAF-PROCS 0`, RSS 3.36GB, held under an `@dr-`-prefixed scope id (differs from the `job-` prefix on healthy scopes, suggesting it arrived via post-restart adoption rather than a normal launch). `ps -p 4096382` returned nothing — the supervisor was confirmed dead. field did not touch it (correctly, per this project's blast-radius discipline) and reported rather than acting.

## What the coordinating session found on investigation, minutes later

By the time this was investigated, the visible job roster had already moved on (different jobs entirely — the `4096382` scope was no longer listed). The "adopted scopes" total at that moment (`52420120576` bytes) turned out to correspond EXACTLY to the summed `Cap` of two different, independently-verified-alive jobs (`ps -p` confirmed both running) — i.e., what was visible at investigation time was legitimate conservative reservation accounting for two real, long-running jobs, not a leak. A daemon restart (done for an unrelated deploy) also did not reveal any additional stale entries: immediately post-restart `adopted_jobs: 0`, and it climbed back to a figure matching real live jobs within seconds as they re-registered.

**So the specific dead-`4096382` entry field found was not independently reproduced here** — it had already self-healed (consistent with the AIRA-74 precedent's own "self-heals as jobs finish" design) by the time this investigation started, a window of at least several minutes. That is the actual open question this ticket records:

## The open question

How long can an adopted-scope ledger entry survive after its underlying supervisor has died, before self-healing removes it? field's report — RSS still shown (3.36GB), scope still counted against the ceiling, supervisor confirmed dead via `ps` — implies at least minutes, long enough to produce a real queued-waiter block on a machine with substantial free RAM. The reconstruction code (`internal/daemon/admit.go`, the `adopted`/`adoptedJobs` loop around the `refreshInterval`-gated rescan) re-derives this from a live cgroup scan each refresh cycle, which should in principle notice a scope has become unpopulated/gone — but the actual latency and the exact trigger for removal were not traced against source as part of this report; that tracing is this ticket's own scope.

## Also found, unrelated, already cleaned up

An orphaned, empty test-artifact cgroup (`aira103probe`) was sitting directly under the real `aira.slice` — left behind by AIRA-103's build agent's own real-cgroup testing, contrary to that build's explicit instruction to use an isolated test slice/cgroup, never the shared one. It was empty (0 processes) and has been `rmdir`'d directly by the coordinating session as a trivial, safe cleanup — not itself connected to the adopted-scope question above, but worth a note in AIRA-103's own follow-up that its test isolation should be checked, in case other real-cgroup tests in that PR have the same leak (harmless when empty, but pollutes the shared slice's directory listing for anyone inspecting it, as it did here).

## Resolution (2026-09-05, backlog-completion triage)

The ticket's own stated scope was to trace the adopted-ledger self-heal path against source; that trace is now done and shows the hypothesised minutes-long stale adopted entry cannot exist in the current code. In internal/daemon/admit.go the adopted ledger is recomputed from scratch on every successful scan (lines 1489-1533), scans are throttled to admitConfineScanIntervalDefault = 1s (line 48), and the evaluator's 250ms ticker (paths.go:43) kicks an evaluation unconditionally with or without waiters (admit.go:1304, 1361-1368), so the ledger is never staler than ~1.25s. Adoption requires leaf Populated > 0 (admit.go:1498); field's row read LEAF-PROCS 0 / LIVE no (a real false, confineBoolYesNo renders nil as "unevaluated"), so by construction it was excluded from adopted within one scan of emptying. That gate has been in place since c533687 (2026-08-27, before the observation) and is pinned by TestAdmitReconstructionSkipsEmptyAndUnknownScopes, TestAdmitReconstructionSelfHealsAfterScopeRelease and TestAdmitReconstructionRefreshIsThrottled (admit_reconstruction_test.go:76-121, 217-233). The "1 adopted scope" in the summary was necessarily a different, live, post-restart-adopted row (several daemon restarts happened today for AIRA-101/102/103 deploys); the table has no per-row attribution, and the coordinating session's later finding (adopted = sum of Cap of two verified-live jobs) is exactly what the code predicts. The @dr- lead is decoded: delegateRAMScopeIDMarker = "@dr" (internal/runner/confine.go:607, IsDelegateRAMScopeID :679) marks every --delegate-ram launch and is not an adoption path; its only adoption effect is the conservative current+margin cap (admit.go:1516-1528). A detached scope id embeds the supervisor's own pid (MintConfineScopeID, confine.go:729-744), so ps -p being empty was a genuine supervisor death, consistent with LIVE no. The only way a dead scope's reserve could persist for minutes is a wedged connection-held outstanding lease (the AIRA-49 class), which is already bounded by defaultStaleLeaseReleaseGrace = 15m from grant (paths.go:94) plus the 5m sweep (paths.go:59) with a subtree-recursive ReapScopeIfEmpty or seen-to-gone proof, and the orphan reaper removes the directory within 2m grace + 5m sweep of dead+empty; confine_reaper.go:135-169 records, with plan-review sign-off, the deliberate decision not to build a liveness probe for a hypothetical wedge, under the project's architectural-simplicity rule (keep the primitive, document the gap). Field's proposed supervisor-liveness-checked scan would be incorrect: orphaned children can outlive their supervisor inside the scope and consume real RAM, which is why population, not supervisor liveness, is the gate. The 3.36GB memory.current on an empty scope is a slice-current matter (file cache discounted via reclaimable; rmdir reparents rather than frees), not a ledger entry. Against CLAUDE.md's bar (primitives not judgement; no new machinery for telemetry-only or hypothetical signals), no action is warranted: the mechanism, its bound, and its regression tests already exist, and a real-cgroup kill-the-supervisor reproduction would only re-measure a kernel cgroup.procs read with no cache in between. What could not be established: the composition of the 62.7GB granted at field's instant, and when supervisor 4096382 actually died (25m46s is scope age since mint, not the dead window); neither changes the conclusion. No code was run or edited (triage only). Suggested resolution note: "Traced against source: adopted ledger is recomputed every <=1s scan with a Populated>0 gate (admit.go:1489-1533), so the observed LEAF-PROCS 0 row was never in it; @dr- is the --delegate-ram marker, not an adoption path; the only minutes-scale hold is the documented, bounded AIRA-49/68 stale-lease backstop. Not reproduced, not a defect." The unrelated aira103probe cleanup note belongs to AIRA-103's follow-up, not here.
