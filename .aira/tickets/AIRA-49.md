Reported live by a peer session (fastest-ee-dc) dogfooding aitest/aira confine on fastest-ee, 2026-09-02 ~21:2x. Repro: `aira confine --delegate-ram -- <long job>`, then kill the wrapping process externally (not via `aira confine --kill`) so the supervisor dies without its own signal-triggered cleanup. Evidence: scope_id `CONFINE-@dr-job-4017698-dl50y3eb6xkj`, supervisor_pid 4017698 confirmed dead via `ps -p` (no such process), yet `aira confine --list` kept reporting the scope as active and still holding its RAM reservation. `aira confine --kill <pid>` (no --steal) correctly refused with `E_CONFINE_OWNER_UNVERIFIED` (their `AIRA_CONFINE_OWNER` was genuinely unset in that session — confirmed by the reporter as expected behavior, not a bug). `--kill --steal` then returned `U_CONFINE_NOT_LAUNCHED: scope ... has nothing to kill yet; retry` on two consecutive attempts, never resolving.

Root cause, confirmed by reading the code: `ConfineKill`'s empty-scope case returned "retry" unconditionally, unable to distinguish "still launching" from "owner confirmably dead, permanently empty"; nothing periodically re-validated a granted waiter's owning PID; the orphan reaper explicitly treats any granted lease as proof of life and skips it — so a waiter stuck in `admitGranted` forever had no automatic recovery path short of a daemon restart.

**DONE + DEPLOYED (2026-09-03, master via PR #3, squash commit `8153255`).** Full two-loop, four plan-review rounds across two independent lineages (Codex/Sol, a Claude Fable reviewer) before implementation — each round found and fixed a real flaw:
- v1: released a lease based on a list-scan's `Populated` field — leaf-only (`cgroup.procs`), not subtree-aware, would have missed a live NESTED child cgroup. Also a TOCTOU race and a no-op bug.
- v2: fixed subtree-safety by requiring the kernel's own removal to succeed before release — but the age signal (scope-directory mtime) started ticking BEFORE admission was even granted, so a job that merely queued under contention could look "stuck" the instant it launched.
- v3→v4: introduced `admitWaiter.grantedAt`, a new timestamp set only at the exact grant transition, immune to admission-queue contention. Confirmed correct by both reviewers via full source traces.
- v5: even `grantedAt`-gated, no signal can PROVE a launcher is dead vs. legitimately `SIGSTOP`ed/paused — resolved by explicitly reframing the 15-minute grace period as a lease-TTL/reclaim POLICY (not a liveness proof), with that trade-off documented plainly rather than chased with more machinery.

Final design: a background sweep reclaims a granted lease only once `time.Since(grantedAt) >= staleLeaseReleaseGrace` (15min default) AND the exact same kernel-enforced physical removal the existing orphan reaper trusts (`ReapScopeIfEmpty`, wrapping `reapEmptyConfineScopeTree`) actually succeeds — never on the age signal alone. Covers every registered admission-queue slice, not just the default.

Adversarial build-review (independent of the implementation): verdict **CLEAN**. Did its own mutation testing (reintroduced each of the four historical bugs into a throwaway worktree, confirmed the new tests catch every one) and independently re-verified lock ordering, multi-slice coverage, the non-Linux build stub, and idempotent release against the real code. Two optional doc-only findings applied before merge.

Verified: `aira confine -- make ci` all 13 packages ok; `AIRA_REAL_CGROUP=1 aira confine -- go test ./internal/runner/... ./internal/daemon/...` both ok (genuinely exercising real cgroup-v2 — this mode hard-fails rather than skips). Deployed: binary rebuilt, atomic swap, daemon restarted, confirmed active.

**Not closed as "root-caused"**: the build-review's independent trace found the *ordinary* connection-close release path should already handle a plain SIGKILL of the launcher (Go sockets are CLOEXEC; a closed connection triggers the daemon's own `cancelPeer`/deferred-`release()` path) — meaning fastest-ee-dc's original repro's true trigger mechanism is still not fully confirmed. This fix is a correct, valuable backstop regardless of what the original trigger turns out to be — a stuck lease from ANY cause now self-heals within ~20 minutes instead of requiring a daemon restart — but the ticket should not claim the original report's specific root cause is confirmed without a live before/after measurement (see the plan's Task 4, still open, not a code task: compare `aira confine --list`'s `slice reserve: <granted>/<ceiling>` line immediately before and after an external kill of the original repro shape).

Also surfaced by build-review, unrelated to this fix: a live dogfood finding — a FIFO head-of-line freeze where one job's oversized/unpinned reservation estimate can block the whole admission queue for its full ~30min timeout even with plenty of ledger and physical headroom sitting idle, invisible without manually checking `ps` (`--list` only shows granted leases, not what's blocking admission behind them). Worth its own AIRA-24-class ticket.
