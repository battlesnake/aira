Reported live by a peer session (fastest-ee-dc) dogfooding aitest/aira confine on fastest-ee, 2026-09-02 ~21:2x. Repro: `aira confine --delegate-ram -- <long job>`, then kill the wrapping process externally (not via `aira confine --kill`) so the supervisor dies without its own signal-triggered cleanup. Evidence: scope_id `CONFINE-@dr-job-4017698-dl50y3eb6xkj`, supervisor_pid 4017698 confirmed dead via `ps -p` (no such process), yet `aira confine --list` kept reporting the scope as active and still holding its RAM reservation. `aira confine --kill <pid>` (no --steal) correctly refused with `E_CONFINE_OWNER_UNVERIFIED` (their `AIRA_CONFINE_OWNER` was genuinely unset in that session — confirmed by the reporter as expected behavior, not a bug). `--kill --steal` then returned `U_CONFINE_NOT_LAUNCHED: scope ... has nothing to kill yet; retry` on two consecutive attempts, never resolving.

Root cause, confirmed by reading the code (not yet fixed):

1. `internal/runner/confine_manage_linux.go` `ConfineKill` (~line 440-457): reads the scope's `cgroup.events` `populated` field via `scope.Empty()`. If the subtree is genuinely empty (which it legitimately is once the wrapped job died and its cgroup drained), the function returns `U_CONFINE_NOT_LAUNCHED: scope has nothing to kill yet; retry` UNCONDITIONALLY -- there is no distinction between "empty because still mid-launch, retry shortly" (the case this error message was written for) and "empty because the owning process died and this state is now permanent" (this case). Retrying literally never resolves it, because the state never changes -- nothing will ever populate that scope again.

2. `internal/daemon/confine_manage.go` `activeConfines`/`freshConfineOwner`/`releaseActiveConfine` all key off `s.admitQueues[path].waiters` entries with `state == admitGranted`. Nothing in `internal/daemon/admit.go` or `confine_manage.go` periodically re-validates a granted waiter's owning PID is still alive (confirmed via grep -- no PID-liveness sweep on admitGranted waiters anywhere). The only release paths are: (a) a normal graceful confine-launcher exit calling its own cleanup, (b) `ConfineKill` actually killing live processes (requires non-empty scope -- see #1), (c) the admit connection's own close being detected server-side (referenced in a comment at confine_manage.go:150-151: "This is the daemon kill-drop release. The admit connection's later close reaches the same state-guarded releaseAdmitWaiter path"). For this bug to reproduce, (c) either didn't fire for delegate-ram's specific connection-holding model, or fired with a delay/race the reporter's session outlived -- not yet distinguished; worth checking whether delegate-ram's per-request admission model holds one long-lived connection for the job's duration the way a plain confine job does, since if it doesn't, there IS no connection whose closure could ever signal "job's launcher died."

3. `internal/daemon/confine_reaper.go` `reapOrphanedScopesPass`'s `hasLiveLease` closure treats ANY `admitGranted` waiter as proof of life and unconditionally skips reaping that scope ("a scope with a granted admit lease is held by a live supervisor and is never reaped" -- by design, and correctly so for the normal case). So a waiter stuck in `admitGranted` forever (per #2) is permanently exempted from the one mechanism (#72/AIRA-36's reaper) that could otherwise clean it up.

Net effect: a scope whose owning process died via anything OTHER than a clean graceful exit or a successful `ConfineKill` (i.e., any external SIGKILL of the wrapping launcher, OOM-kill of the launcher itself rather than the payload, etc.) can permanently hold its ledger reservation with NO automatic or manual recovery path short of a full daemon restart (which per AIRA-74 reconstructs reserves from live scope `memory.max` on restart -- a scope with no live process to read `memory.max` from presumably drops out of that reconstruction, but this hasn't been verified either).

Impact: reduces effective slice admission capacity for every session sharing `aira.slice` until the daemon is restarted; a stuck scope is invisible to `--kill`, `--kill --steal`, and the reaper alike.

NOT yet fixed -- correctness-critical work on the admission ledger/lease state machine, per CLAUDE.md's two-loop mandate (same class as AIRA-67/72/74). Candidate fix directions (not designed here): (a) give `ConfineKill`'s empty-scope case a way to distinguish "genuinely still launching" from "owner confirmably dead, nothing will ever populate this again" (e.g. age since grant + a PID-liveness check on the recorded supervisor PID) and treat the latter as a terminal release-and-succeed rather than `U_CONFINE_NOT_LAUNCHED`; (b) have the reaper (or a new sweep) periodically re-validate `admitGranted` waiters' owning PIDs via pidfd/ESRCH and release+deregister ones that are confirmably dead, rather than treating `admitGranted` as unconditional proof of life forever; (c) confirm/harden the admit-connection-close release path for delegate-ram specifically.
