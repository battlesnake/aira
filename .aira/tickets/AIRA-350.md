Owner decision 2026-11-18 (supersedes the earlier dynamic lane, which could not prove a head cannot starve): "go back to a fixed slice that is separate to the main slice reservation. Its max size is always fixed. The main slice reduces its admission ceiling based on available RAM as it currently already does." Earlier wording: "a fixed slice of x GB (4 or 8), which jobs requesting <= y GB (1 GB) are admitted to before using the main slice; if full they use the main slice; default mode only, not CI mode."

Design (spec round 2; round 1 put the lane on top of today's ceiling and was re-based): a separately-booked pool of fixed size x inside the one queue and ledger (AIRA-228; not a second cgroup). The lane comes OUT of today's ceiling: the main pool's room is today's effective maximum (still reduced with available RAM exactly as today) less x, so the machine is protected exactly as today (sliceceiling.go:319-325 refuses a throttle target inside the watchdog kill band; adding x on top would put it there). Every grant in either pool passes today's fit on the whole slice; main grants also pass the main pool's ledger room on E - x, which reads no lane state. A job-level waiter whose ledger charge is <= y (not a sub-reservation, exclusive or suite parent) is tried in the lane first, while lane occupancy (reserve + 64 MiB per job, the cap) + its own <= x, past the head-of-line freeze and bypass budget, leaving the head's CPU and VRAM; closed behind a pushed head. Lane full or job larger: the main pool, as today. Restart: an ARDR lease with no parent and reserve <= the largest lane reserve returns to the lane (order-independent). Spec: docs/superpowers/specs/2026-11-18-fixed-small-lane-design.md. Correctness-critical (admission, host memory): two-loop, Opus builds, Fable reviews, Sol xhigh.

Evidence and prior review: docs/superpowers/specs/2026-11-18-small-job-lane-design.md (dynamic lane, 4 rounds, not approved) and docs/dev/aira-350-*.
