Found by a `/code-review high` pass launched during AIRA-84 (Fix 4, the symmetric daemon deadline-policy seam, PR #25) — the review completed but its findings routed to the coordinating session rather than back into the build agent that launched it (a nested-agent-dispatch notification-routing quirk), so this was recovered and posted to the PR as a comment; filed here as its own ticket since it stands on its own regardless of what lands in that PR.

## The gap

`cmd/aira/mcp.go`'s `Serve` loop is strictly serial: one JSON-RPC request runs to completion before the next line is even read (`mcp.go:278-303`). It is started with `context.Background()` (`cmd/aira/main.go:75`), and that same deadline-less, cancellation-less context flows straight into `dispatcher.Dispatch(requestContext, scope, request)` (`cmd/aira/mcp_project.go:73`).

AIRA-84 (Fix 4) introduced a real, deliberate `ResponseWait` bound (6 minutes) that the client side now falls back to whenever the caller declares no context deadline of its own — which the MCP path never does. So against a wedged (not crashed, not OOMed — genuinely hung) daemon, a single routed MCP tool call now blocks for up to 6 minutes, and because the loop is serial, every subsequent MCP tool call from the same agent session is blocked behind it for that same window. Unlike a CLI invocation, there is no SIGINT recourse: the MCP server is a background subprocess of the agent host, not something an interactive terminal can Ctrl-C.

This is a real behavior change AIRA-84 introduced without reasoning about it — its own plan (section 4.2) and ticket only reason about the CLI face. Before AIRA-84, this same scenario hit the old (buggy, dishonest) 30-second connect-deadline reuse and failed faster, just with a wrong/unclear reason. AIRA-84 fixed the honesty problem (no more OUTCOME_UNKNOWN from a stale deadline) but, for MCP specifically, made the failure mode slower and unrecoverable rather than fast and wrong.

## Suggested direction, not decided/built

Two candidates, not mutually exclusive:
1. A per-request deadline at the MCP dispatch seam (`mcp_project.go:73`) — bounds each call without a new config knob, but the "right" number is a judgement call: too short risks failing legitimate long-running MCP calls (a real `gate attest`, `reconcile --rebuild`) prematurely; too long doesn't meaningfully improve on the current 6-minute exposure.
2. Propagate real signal-based cancellation into the MCP server's context, matching the pattern other entry points already use (`cmd/aira/tui.go:80`, `main.go:1008`, `main.go:1164`, `cmd/aira/daemon_command.go:43` all install a signal handler; the MCP entrypoint at `main.go:75` does not). This is more architecturally consistent than picking an arbitrary timeout, and gives at least an external recourse (a signal sent to the MCP host process) even though there is still no interactive terminal to send it from directly.

Not scoped, not built. Whichever direction is chosen needs its own two-loop given it touches daemon-facing MCP request handling.

## Resolution (2026-09-05, backlog-completion triage)

STATUS OF THE MECHANISM (verified against master 3251bed, not the ticket's prose): every fact the ticket names is still exactly true. `cmd/aira/main.go:87` starts the MCP server with `context.Background()` (last changed in 7b5b61b, long before the recent churn; no signal handler). `cmd/aira/mcp.go:298-324` `Serve` is strictly serial (`ReadString` -> `handle` runs to completion before the next line is read) and has no `notifications/cancelled` path (it would fall to -32601 and cannot be read while blocked anyway). `cmd/aira/mcp_project.go:87` hands that same deadline-less context to `dispatcher.Dispatch`; `cmd/aira/dispatcher.go:128-158` adds no budget; `exchangeWithReplacement` (:387) only handles protocol-version replacement and `exchangeOrStartUsing` (:442) only retries on `CodeUnavailable` (crash/absent), never on a hang. `internal/daemon/protocol.go:420` therefore falls back to `ResponseWait` = 6m (`deadlines.go:98`). Routed verbs still carry no daemon-side execution budget (`deadlines.go:75-86`; AIRA-84 plan §7 deferral, untracked by any ticket). None of AIRA-101/102/103/64/97/74/78/89 touched this seam (last-touch: mcp.go/mcp_project.go by AIRA-87 exit-code move only; deadlines.go by AIRA-84 itself). So it is NOT already-done and NOT superseded.

WHY IT DOES NOT WARRANT ACTION, against the project's own bar:

1. The ticket's candidate #1 (a per-request deadline at the MCP seam) is either regressive or vacuous, and the AIRA-84 two-loop already ruled on exactly this. Any value below 6m re-creates the AIRA-84 defect from the MCP face: the daemon's sanctioned heavy budget is 5m + 30s write, so a legitimately slow `import` / `gate attest` / `reconcile --rebuild` would commit and be reported OUTCOME_UNKNOWN -- the project's stated worst failure direction ('a lie about work that happened', deadlines.go:34-37). The AIRA-84 plan-review record (§8) explicitly rejected Gemini's shorter-default proposal and a knob on precisely these grounds, and DeepSeek drove the value DOWN to the smallest the derivation permits. Any value at or above 6m changes nothing versus the existing fallback. The only honest closure is a daemon-side per-verb routed budget, which is an owner-accepted AIRA-84 deferral (plan §4.2 'documented gap', §7, §9 build-review 'not fixed, overclaim removed') and is explicitly new machinery against the standing simplicity rule.

2. The ticket's candidate #2 (signal.NotifyContext at main.go:87) buys nothing that does not already exist. The `aira mcp` process installs no handler (the only `signal.Ignore` is SIGHUP in the confine --detach path; `core/command.go:84` forwarding is transient during a client-routed `run` and is `signal.Stop`ped), so SIGINT/SIGTERM take Go's default disposition and terminate the process today -- `kill <pid>` of the MCP child already works, and the host observes the subprocess die. `protocol.go:388`'s `context.AfterFunc(ctx, conn.Close)` means a NotifyContext WOULD unblock the read, but the result is a permanently-cancelled context: `Serve` keeps reading stdin and every subsequent Dispatch fails at `DialContext` -- a half-dead server until the host restarts it, i.e. equal-or-worse than the abrupt exit unless more machinery (exit-on-ctx.Done, cancel-notification handling) is added. The sibling handlers the ticket cites exist for cleanup obligations the MCP server does not have (tui.go restores the terminal; daemon_command.go shuts the daemon down gracefully; main.go:1275/1439 are streaming loops). The ticket's 'no SIGINT recourse' is really 'no interactive terminal', which no code change fixes.

3. The one change that would actually address head-of-line blocking within an agent session -- a concurrent MCP request loop with `notifications/cancelled` support -- is precisely the class of feature-specific machinery the owner's HARD rule (keep AIRA architecturally simple; 'keep the primitive + document the gap' over new mechanisms) forbids, for a scenario that (a) the ticket itself frames as hypothetical, (b) has no observed instance anywhere in .aira/ (every 'wedged' hit in other tickets is theoretical or a deliberately-wedged test relay), (c) is by the AIRA-84 text 'a daemon bug in the first place', and (d) hits every face equally -- each CLI call against the same wedged daemon also blocks 6m.

Net: this is a real but already-adjudicated accepted cost (AIRA-84 §4.2) viewed from the MCP face; both directions the ticket proposes are non-improvements on inspection, and the only effective fix is disallowed machinery for an unobserved daemon bug. The project's own convention is that accepted gaps are written down, not silent -- so the correct disposition is close with a resolution note (see build_notes for an optional one-sentence doc-only addition to make the MCP facet of the gap explicit where the CLI facet is already documented).

WHAT I COULD NOT ESTABLISH: how the MCP host (Claude Code) itself behaves on a stuck tool call -- whether it applies its own per-call timeout and whether it restarts the server. This does not change the analysis: a host timeout alone leaves the serial server still blocked, so subsequent calls still queue until the host restarts the process, which it can do today via the default signal disposition.
