Owner directive 2026-08-28: -n auto (one worker per core) must be the SANE DEFAULT; AIRA owns maximising utilisation WITHOUT OOMing. Where OOM still happens, either add per-test RAM annotations OR fix AIRA. Infra report (real): merge-gate -n auto LITE runs (--delegate-ram, aira_xdist_governor registered in conftest) kept OOMing under other sessions' 15G+13G jobs on the shared 64G slice; a session fell back to a SERIAL run to get a definitive green. So the per-test RAM governor is NOT preventing aggregate slice OOM under contention. Likely mechanism: the per-test RESERVATION is an admission-ledger ESTIMATE, not a hard per-worker cap — if a worker's actual RSS exceeds its reserved bytes (framework default too low / no per-test aira_mem / high-variance test), Sigma(actual) can exceed cap-headroom -> oom.group kills a victim EVEN under the governor. Directions: (a) better per-test estimates (raise the framework default, annotate heavy tests, lean on peak-RSS history); (b) OPTION: enforce the reservation as a per-test hard memory.max on a per-test sub-cgroup so a worker physically cannot exceed it (trades a possible false-kill for a hard no-aggregate-OOM guarantee); (c) confirm admission actually BLOCKS a per-test reservation when the slice is reserve-saturated by OTHER sessions (vs letting it run and racing to OOM). Counterpart to AIRA-11 (the CPU/bootstrap half). Needs a contention repro.

CONSTRAINTS + REFRAME (owner 2026-08-28): (1) the 512MB per-test default is a DELIBERATE conservative over-estimate with headroom for slightly-under-spec'd tests, so it must stay a SOFT admission reservation, NOT a hard cap — enforcing memory.max=512MB per test would false-kill the many tests that legitimately use a bit more. This RETRACTS the per-test-hard-cap direction above. (2) Suites can have THOUSANDS of light/quick tests, so per-test overhead must stay minimal — a per-test cgroup create/destroy is too costly, and even the per-test `confine-reserve` daemon round-trip is suspect at that scale; prefer AMORTISING (a per-worker STANDING reserve held across tests, re-reserved only when a test needs more) over per-test work. KEY REFRAME: because the 512MB default OVER-estimates, admission SHOULD already bound the aggregate conservatively (Sigma reserved >= Sigma actual) — so an OOM under it is most likely an ACCOUNTING/ENFORCEMENT bug, not a too-low estimate: candidates = other sessions' WHOLE-JOB reserves under-estimating their actual (the [[AIRA-6]] reserve!=actual footgun), a reservation leak / release-before-RSS-frees timing gap, or too-thin slice headroom. So the fix is "make the slice-level aggregate accounting actually hold" (owner: fix bugs in aira). The repro must MEASURE where Sigma(actual) exceeds Sigma(reserved) rather than assume the per-test estimate is wrong.

MEASURED SIGNAL + LIKELY ROOT CAUSE (altium, 2026-08-29, /usr/bin/time -v under aira confine -n0): a single skfem test peaked ~1.25GB (tagged aira_mem 2G), another ~848MB (tagged 1G) — BUT the decisive datum: test_fe_impedance.py + test_impedance_analysis.py IN ONE PROCESS peaked ~2.19GB via memo-cache (segment_fe_z0) accumulation ACROSS files. This pinpoints the granularity bug: xdist WORKERS ARE LONG-LIVED PROCESSES whose RSS ACCUMULATES across the many tests they run (caches, module state, memory not freed between tests). A worker's real footprint is its CUMULATIVE high-water mark, NOT the current test's reservation. So Sigma(per-test reservations) charges one test per worker at a time, while Sigma(actual worker RSS) = Sigma(cumulative worker peaks) and grows over the run — a structural under-count no per-test estimate can fix (the 512MB default and even accurate aira_mem are per-test; the leak is cumulative). Compounded by the engine leg's `load` dist (not loadscope): accumulating files can co-locate on one worker and stack. LIKELY-REAL FIX (supersedes 'better per-test estimates'): reserve PER-WORKER against the worker's MEASURED actual RSS — each test, the governor samples the worker's real RSS (/proc/self/statm or the worker's cgroup) and reserves max(aira_mem-estimate, measured_RSS + growth_headroom), so the reservation tracks the cumulative footprint automatically and aira_mem only needs to cover a test's transient spike above the running baseline. Cheap (statm read per test, no cgroup churn) and respects the amortise constraint. Alternatives: a per-WORKER memory cap (one cgroup per worker — low overhead, hard-bounds cumulative, but sizing/false-kill risk), or recycle a worker when its RSS crosses a threshold. CAVEAT: these skfem tests importorskip in the locked CI env (no scikit-fem) so they SKIP in the standard engine leg; they only draw this RAM under a scikit-fem overlay — altium's annotations are defensive.
