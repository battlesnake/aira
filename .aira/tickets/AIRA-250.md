Owner (2026-09-14): central secrets/token management. gcloud auth -> 1h oauth token -> mint 12h impersonation SA tokens. Want central management (not agents doing the token dance + leaking + poor cross-session discoverability). Tokens visible to an agent = determined by the PROJECT (git repo/remote). Where possible AIRA delivers tokens directly (env-vars / .aws / gcloud plugins) rather than handing them to agents. Different projects have different gcloud projects/roles => their own token sets per key (gcloud, aws). Minimise how often agents access/know where secrets are stored.

DESIGN DIRECTION (proposal, NOT approved): AIRA = token BROKER + INJECTOR, not a store agents read.
(1) Central daemon holds the owner's ROOT grant and mints/refreshes derived (12h SA) tokens; owner authenticates ONCE.
(2) Machine-wide project->credential-profile map, keyed by the SAME git-remote identity AIRA already computes (FEE/namespacing) => "tokens visible = determined by project" for free; gcloud/aws are KEYS, each project has its own value.
(3) INJECTION not exposure: extend the confine/run launch seam (already sets child env + cgroup) to deliver creds into the CHILD process only, by each tool's native mechanism (GCP: CLOUDSDK_AUTH_ACCESS_TOKEN or an ephemeral GOOGLE_APPLICATION_CREDENTIALS file; AWS: short-lived AWS_* env or a per-launch shared-credentials/process-provider). Minted just-in-time, scoped to the launch, never printed, never in the agent's transcript/reasoning context. Agent runs `aira run --with-creds -- <cmd>`; never runs auth, never sees the token, never knows the storage path.
(4) Central mint+cache+refresh: one refresh serves every session/worktree; central revocation + audit log (which project minted what when) — a natural fit for AIRA's lease-ledger style.

OWNER CORRECTION (2026-09-14): "mint the 12h SA tokens on demand won't always be possible — the 1h root oauth expires and I sleep several hours per day." Real constraint: during a long sleep there may be no valid root to mint fresh derived tokens from. Refinement:
(A) FIRST establish whether the owner's gcloud credential carries a durable REFRESH token. The normal `gcloud auth login` stores one, and `gcloud auth print-access-token` auto-refreshes the 1h access token from it WITHOUT re-auth, for a long time until revoked. If so, AIRA reuses THAT (via gcloud's own store / print-access-token) and can mint fresh access->SA tokens right THROUGH the owner's sleep — the problem largely dissolves. OPEN Q for owner: does your setup yield a durable refresh token, or a bare 1h token (org/MFA policy)?
(B) If genuinely bare-1h-only: AIRA must EAGERLY pre-mint the longest-lived derived (12h SA) tokens while the root is valid, as LATE as possible before root expiry to maximise reach; track both root+derived expiry; surface "coverage until T / re-auth needed by T"; and accept a DOCUMENTED gap when a sleep outlasts derived coverage. Tradeoff to offer the owner: a longer-lived root (a service-account KEY stored centrally = 12h+/non-expiring, no interactive re-auth) buys sleep-through coverage at the cost of a higher-value long-lived secret on the box.

HONEST LIMITATION (unchanged): a token in the child's env is readable by any command the agent constructs (env, cat $creds_file) — so "never handed to agents" is BEST-EFFORT when the agent controls argv. Real wins: no token in the agent's context/transcript, no repeated auth, per-project scoping, short TTL, central refresh + revocation + audit. True run-but-cannot-read isolation is a separate, harder problem (broker-side API proxying, or a restricted exec that scrubs env from agent view).

MINIMAL FIRST SLICE if pursued: reuse gcloud's own credential store (refresh-token-capable) + project->gcloud-profile map + `aira run` injecting CLOUDSDK_AUTH_ACCESS_TOKEN just-in-time, cached+refreshed centrally. One tool, one injection mechanism. AWS/plugins/revocation-UI later. NOT for any specific release yet — backlog.
