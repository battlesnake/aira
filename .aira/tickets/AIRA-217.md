confine's estimated-cap OOM advisory asserts "The kill is now recorded" for a best-effort peak report whose error it discards
**kind** bug · **severity** P3 · **closes** RANT-19

**SYMPTOM.** A job OOM-killed at an AIRA-estimated cap prints "The kill is now recorded against this command's signature: RE-RUN THE IDENTICAL COMMAND and the next admission is sized higher on its own … If an identical re-run is killed at the same cap again, that is a genuine bug worth reporting." Both arms are unconditional. The recording they assert is best-effort and is the only thing that makes the re-run remedy true; when it silently fails the operator re-runs a heavy job that is admitted at the same reserve and killed again — and is then told to report AIRA's own dropped write as a bug. Nothing corrects the claim: `FormatConfineStatus` has no field saying whether the sample landed.

**ROOT CAUSE.** `internal/runner/confine_linux.go:1399` — `_ = deps.reportPeak(reportCtx, request, ConfinePeakReport{...})` under a 250 ms `context.WithTimeout`, error discarded. That report is the only producer of the record (`store.RecordConfinePeak` has one non-test caller). The signal is definite and already in hand: `ReportPeakSample` returns an error unless `response.OK && response.Code == "OK"` and the daemon replies `{"recorded": true}`. `formatConfineReserveAdvisory` (`:1607`) has no such parameter, yet it is called at `:1464` inside the same function and strictly after the report — the value is in scope. History: `.aira/tickets/AIRA-133.md:157-159` logged this as an accepted wording nit; AIRA-184 then reworded and **duplicated** the assertion into both new arms (`:1664`, `:1685`) without revisiting it.

**PROPOSED FIX.** Capture the outcome as `recorded` / `not-recorded` and branch the sentence. For the `recorded` path keep today's wording exactly. For `not-recorded`: say the kill could not be recorded, say the next admission will **not** be sized higher, and drop the "genuine bug worth reporting" clause, since a dropped report is precisely what produces that repeat. **The over-ceiling arm (`:1664`) needs its own remedy and must not be told to name a pin** — that branch is entered when `suggested >= sliceCapBytes`, i.e. a pin the slice cannot hold, and naming it is the exact wording AIRA-184's build review BLOCKed; its honest not-recorded remedy is "split the heavy work or use a larger slice". Optional and the natural home: a `peak-report=recorded|failed` facet on `FormatConfineStatus`. Treat the third `unevaluated` state as a zero-value default only, not an operational case — `signature == ""` requires an argv confine rejects before launch. **Explicitly not proposed:** retries, a spool, a second recording path, or a wider deadline. Scope note: the delegate-ram arm (`:1688-1690`) and default arm (`:1694`) assert no record, so neither is false and neither changes.

**HOW TO TEST.** The `deps.reportPeak` seam already exists and is stubbed (`internal/runner/confine_termination_linux_test.go:262`): stub it to error, force an own-cap OOM at an `auto:daemon-reserve` cap, and assert the advisory reports the failed recording, does not contain "The kill is now recorded", and does not contain "a genuine bug worth reporting". Note the negative control already exists — `internal/runner/confine_linux_test.go` pins the full expected string for **three** daemon-reserve rows plus two over-ceiling rows, so the fix must update those goldens, not add one.
