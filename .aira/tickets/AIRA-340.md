Owner request 2026-11-14: a way for a job to say it is high priority when it is launched, so that it is queued and dispatched ahead of lower-priority jobs. Today the only way is to wait until the job is queued and then push it with `aira confine --front <name|pid|scope-id>` (`f` in `aira top`), and a daemon restart drops the push. Nothing at launch, and the queue is otherwise first-come first-served (plus AIRA-307's small-job bypass of a frozen head).

## Decisions already taken (owner + coordinator; do not re-litigate, challenge only if a counterexample appears)

1. Flag name: `aira confine --priority high|normal` (default `normal`; any other value is refused with a stable code). NOT a launch flag named `--front`, because `--front` is already a standalone verb with a different meaning (one name, two meanings). `--priority` is QUEUE ORDER ONLY: say so in the skill text and the help; it is unrelated to the cpu.weight ageing.
2. Semantics = "pushed at enqueue", reusing the existing mechanism (admitWaiter.pushSeq, admitOrderLocked in internal/daemon/admit.go, the freeze/bypass rules for a pushed head), with ONE difference: among launch-time `high` jobs the order is FIFO (their enqueue order), not latest-first. Reason: with latest-first, a box where every session marks its jobs high degenerates to newest-first and starves older jobs. Target evaluation order: (a) waiters pushed by `--front` (latest push first, unchanged), then (b) `high` waiters in enqueue order, then (c) every other waiter in enqueue order. It must stay the single source for the evaluator, the client's "queue position N of M" line, the queued-ahead bytes and the `aira top` rows (see the comment above admitOrderLocked).
3. A high job that does not fit holds the jobs behind it exactly like a pushed head does today (fairness freeze), and AIRA-307's bypass budget applies to it like any head. Keep one rule, not two.
   AMENDED at build (2026-11-14): the two halves of this decision contradict each other. A pushed head has no bypass budget and no backstop pass: nothing behind it is granted until it fits (`case head.pushSeq > 0` in the head-protection switch in `internal/daemon/admit.go`), so a head that has a budget is not held "exactly like a pushed head". The reading built is the second half: a `high` head is an ORDINARY unpushed head. A job behind it is granted on fit within the head's bypass budget (half its reserve), a jumper over the budget is held and arms the duty cycle, and the backstop pass (freeze yield) still grants on fit. Pinned by `TestAdmitHighHeadUsesTheBypassBudgetNotThePushedRule` (internal/daemon/admit_priority_test.go). Why: `high` is chosen at launch by hooks and Makefiles across every project on the box, with no per-session cap, so the strict pushed rule would let one misused or oversized `high` job wedge the whole slice until it fit; `--front` can afford that rule because it is an operator's one-off act on one queued job. The budget plus the backstop limit a misused `high` to the same bounded hold any large head already imposes, and "one rule, not two" still holds (the AIRA-307 head rule, unchanged). The strict pushed-style hold, if wanted later, is a two-site change: that switch (`case head.pushSeq > 0 || head.high:`) AND `admitReportedPhaseLocked` (so `--list` and `aira top` report the freeze as pushed, not idle), plus flipping that test's expectations.
4. `high` is a property of the REQUEST, carried on every admit request the client sends, so it survives a client reconnect/re-declare after a daemon restart (unlike a `--front` push, which is dropped; leave that behaviour unchanged).
5. Not selectable for aitest worker/sub-reservation claims or `confine-reserve` waiters; those are not affected (they have no launch flag). `--priority` on a launch that never reaches the queue (admitted immediately) is simply a no-op. In ci-shim mode it must behave like `--front` does there (queue-state only) or be a documented no-op; the builder decides from the code and pins it with a test.
6. Purpose and who sets it (owner clarification 2026-11-14): the point is that SHORT, automated jobs, such as pre-commit hooks and pre-gate steps, do not wait long behind slow ones. The `--priority high` argument therefore lives in the hooks and Makefiles themselves (project-level wiring decided once), NOT in agents' ad-hoc calls. Agents must avoid `--priority high` in direct `aira confine` calls unless it is strongly justified, which should be rare (for example a human is blocked right now on a one-off short command and there is no hook/Makefile that could carry it). The skill text, the generated help and the MCP/tool descriptions (all from the dispatch tables) MUST say this in plain words: priority is queue order only; set it in the hook or Makefile for short gates; agents do not use it by default; a long job (a full test suite, a build, `make ci`) is never `high`, because a high job that does not fit freezes everything behind it. Also add the same sentence to the project-level guidance an `aira install` writes for other projects, if the install step has such a template (find where the skill text reaches other projects).
   No per-session cap in this ticket (a cap is judgement). Abuse must be observable instead: `aira confine --list` queued rows and `aira top` show the priority (a `priority` field on queued rows, a marker in top). If misuse shows up in rants, a follow-up can add a cap.
7. Wire: add an optional field to the admit request frame (absent = normal). The builder must determine whether an old daemon tolerates an unknown field in that frame or rejects it, and bump DaemonProtocolVersion on BOTH sides (TestRunnerDaemonProtocolVersionMatchesTheDaemon) only if needed; state the finding in the PR. A new client talking to an old daemon must fail honestly or degrade honestly to normal with a visible notice, never silently claim priority it did not get.

## Acceptance / invariants to pin with tests (mutation-verify each)
- Order: with N queued normal jobs, a later-launched `high` job is dispatched before them; two `high` jobs dispatch FIFO; a `--front` push still beats a `high`; a normal job never overtakes a high one except through the existing bypass budget.
- Ledger sum of granted charges unchanged; no leak; head/freeze/bypass/exclusive-gate state has no ghost after a high waiter is cancelled (AIRA-328 `--kill`), times out, or is granted.
- Reconnect after a daemon restart keeps `high`.
- The client's queue-position line, the queued-ahead total and the `aira top` / `--list` rows agree with the evaluator (one ordering function).
- Skill/help/MCP text: a test (like the existing skill-text tests) that the generated skill and help contain the 'rare, set in hooks/Makefiles, never for long jobs' guidance.
- `--priority` values: `high`, `normal` accepted; anything else refused with a stable code; no value or duplicate flags refused like the sibling flags; dispatch-table help, MCP schema and skill text updated from the tables.
- Grant-vs-cancel race under -race -count=20 still XOR.
- Cutover: DAEMON + client change (client install AND `systemctl --user restart aira-daemon.service`); old-client/new-daemon and new-client/old-daemon behaviour stated.

## Wire it into aira's own hooks and Makefile (small, same PR)
Apply `--priority high` ONLY to genuinely short steps in this repo's own automation: the pre-commit hook's quick checks (vet/build) and the Makefile's short pre-gate steps if they are launched through `aira confine`; find them (`.githooks/`, `Makefile`, `ci/` scripts) and list in the PR which steps got it and each step's measured wall time (from a trailer) that justifies it. The full `make ci`, test suites and anything over about a minute stay `normal`. If a step's duration cannot be established, leave it normal and say so.

## Out of scope
A numeric priority scale; preemption of running jobs; a per-session cap; changing `--front`'s semantics; CPU priority; AIRA-326's automatic fast lane (a separate, held, history-driven mechanism that should reuse the same ordering function when it is built).
