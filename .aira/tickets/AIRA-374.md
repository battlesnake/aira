Owner 2026-11-22: 'aira top is incredibly laggy now.' Evidence at the time: load average 75-87 on 16 cores, CPU PSI some avg10 74%; confine --list --json takes 56 ms wall (daemon is fast); the aira top process used about 8% CPU, all user time (40 ticks in 5 s), sys near 0, on a 72 KB list reply of 27 running + 4 queued rows whose command strings run up to 4096 bytes. Needs: a committed benchmark of the per-tick path on a recorded reply, a bisect against earlier commits (88193837 AIRA-361 lane display, 798af794 AIRA-368 supervisor argv) to see whether it regressed, and the fix (candidates: wide-string width/truncation work on 4 KB commands each frame, per-tick allocation/GC, re-render on every tick when nothing changed, input handling blocked behind render).

Investigation 2026-11-22 (branch aira-374-top-lag). The owner's lag is on keystrokes. An up/down arrow runs no fetch and no view-model rebuild: tview redraws the whole screen after every key event, with no coalescing, and its Table measures the full grapheme width of every visible cell three times per draw (column sizing, print, ellipsis check). Nine ~4 KB supervisor argvs in the listing made that cost about 23 ms of CPU per keypress and 25 ms per 1 s refresh tick at 200x50 (BenchmarkTopKeypress / BenchmarkTopTick on the recorded reply; 70-75% of it in tview.TaggedStringWidth / uniseg). Box load stretched wall time to 1.2-2.5x CPU time, and a held arrow queued redraws.

Bisect (same benchmarks, recorded reply, 200x50, CPU per op): no client regression. Keypress 21-24 ms and tick 24-30 ms at 9f36dc51 (before AIRA-361), 88193837 (AIRA-361), 798af794 (AIRA-368) and 6804ab83 alike, allocations flat. The cost is the long command strings in the data, not a code change in aira top.

Fix: the COMMAND/DIRECTORY cell (and the SESSION pane label) is cut at 512 input runes before escaping, marked with "…". Keypress ~23 ms to ~10 ms, tick ~25 ms to ~14 ms.
