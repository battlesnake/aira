## Symptom (found during the whole-project simplification review, PR #12, verified independently against source)

The installed `SKILL.md` (generated by `internal/core/skill.go:326`) tells agents: *"Launch the whole invocation under a plain `aira confine -- pytest --aitest-workers=auto ...` — no `--delegate-ram`, no `--memory-reserve`... aitest's own supervisor forks each worker and admits it individually through the daemon (`worker-admit`), which places it in its own kernel-enforced cgroup sub-scope..."*

This is the documented, recommended, agent-facing way to run aitest — and it is wrong. `internal/runner/confine_linux.go:757-777`:

```go
if request.DelegateRAM {
    // aitest is only meaningful for a delegate-RAM launch (worker-admit
    // grants nested sub-scopes under THIS job's own outer scope)...
    cmd.Env = pylib.AppendAitestChildEnvironment(cmd.Env, request.RuntimeDir, diagnostics, reserveCommand)
} else {
    // Strip unconditionally, not just skip appending (Fable build-review,
    // final gate)...
    cmd.Env = pylib.StripAitestEnvironment(cmd.Env)
}
```

Without `--delegate-ram`, the AITEST_* coordinates aitest's supervisor needs to reach `worker-admit` are not merely left unset — they are **unconditionally stripped**, deliberately, per an explicit comment from a past build-review (guarding against a *different* problem: stale coordinates leaking from a parent job). The documented invocation (no `--delegate-ram`) therefore guarantees aitest never has what it needs to place workers in kernel-enforced cgroup sub-scopes, and falls through to its own reduced-worker, no-cgroup-placement fallback path — the exact path SKILL.md itself describes as only happening "if the daemon is unavailable," except with the documented invocation it happens unconditionally, daemon up or not.

## Why this matters

This is the same "asked for X, silently got Y, told nothing" pattern found and fixed repeatedly tonight (AIRA-51/58/59/62) — except this one is live in the officially-generated, currently-deployed skill documentation that every agent using this project is told to follow. Anyone who used the documented form tonight (or since it was written) got zero RAM containment on their pytest workers while believing, on AIRA's own authority, that they had kernel-enforced per-worker caps.

## What needs deciding, not just fixing

Two candidate directions, and the choice needs real judgment rather than a blind edit:
1. **Fix the code**: make aitest's coordinate-wiring not depend on `request.DelegateRAM` — aitest doesn't need whole-job delegate-ram semantics, only its own coordinates to reach `worker-admit`. Risk: understand exactly why the current gate exists (the `AppendConfineChildEnvironment`'s "own delegateRAM gate" referenced in the comment above) before touching it — there may be a real reason coordinates are scoped to delegate-ram launches that isn't just "this is where aitest happens to be documented."
2. **Fix the doc**: change SKILL.md to recommend `--delegate-ram` for aitest after all. Risk/complication: the same review (PR #12) separately found that `--delegate-ram` arms BOTH the xdist governor's per-test reservations AND aitest's per-worker caps if a project loads both plugins — recommending `--delegate-ram` unconditionally might reintroduce that double-booking for a project still transitioning off xdist.

Whichever direction, this needs the same rigor as other daemon/runner-adjacent fixes tonight (external review, TDD) given the correctness stakes and the fact it's already deployed and being actively relied on.
